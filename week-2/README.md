# Week 2 - LangChain Practicals

A clean, installable Python project demonstrating four LangChain practicals:
**reusable prompt templates**, **model invocation methods**, and a **structured
review-analysis pipeline**, all under proper project management via
`pyproject.toml` (no `requirements.txt`).

## Project layout

```
week-2/
├── pyproject.toml              # build config + pinned dependencies + console script
├── .env.example                # template for API keys (copy to .env)
├── data/
│   └── reviews.json            # 10 realistic human-written reviews (mixed sentiment)
├── outputs/                    # generated comparison tables, results, reports
├── src/langchain_practicals/
│   ├── config.py               # .env loading + settings (no hardcoded keys)
│   ├── models.py               # provider factory (Groq / Mistral / Google)
│   ├── prompts.py              # Practical 1 - prompt templates + LCEL
│   ├── model_invocation.py     # Practical 2 - invoke/stream/ainvoke/astream
│   ├── review_pipeline.py      # Practical 3 - structured review analysis
│   └── cli.py                  # `langchain-practicals` entry point
└── tests/
    └── test_review_pipeline.py # hermetic pytest suite (fake models, no keys)
```

All four practicals are covered by the same package; the **Project Management**
practical *is* the packaging/dependency/isolation setup shown here, verified by
`pip install -e .`, a `.env.example`, sample `data/` + `outputs/` directories,
reproducible pinned deps and a pytest suite.

## Setup

Requires Python 3.10+. The project is installed as an editable package using
`pyproject.toml` (hatchling backend) — there is **no** `requirements.txt`.

```bash
cd week-2
python3 -m venv .venv
source .venv/bin/activate

# Install the package + its pinned dependencies (+ dev extras for pytest).
pip install -e ".[dev]"

# Provide your own API keys (never commit .env).
cp .env.example .env
# Then edit .env and paste in your GROQ_API_KEY / MISTRAL_API_KEY / GOOGLE_API_KEY.
```

> Every provider key is read from the environment at runtime. If a key is
> absent, that provider is simply skipped — so commands degrade gracefully.
> Practical 3 compares **at least two** providers, so configure two or more keys.

## How to run each part

```bash
# Practical 1 - Prompt Templates (prints formatted messages + an LCEL chain)
langchain-practicals prompts

# Practical 2 - Model Invocation Methods (times invoke/stream/ainvoke/astream)
langchain-practicals models

# Practical 3 - Review Analysis Pipeline (all configured providers)
langchain-practicals reviews

# Practical 3 - limit to specific providers
langchain-practicals reviews --providers groq mistral

# Run everything
langchain-practicals all
```

You can also run the modules directly, e.g. `python -m langchain_practicals.prompts`.

Outputs are written to `outputs/`:

| File | Generated by | Contents |
|------|--------------|----------|
| `comparison_results.json` | `models` | per-method timing (total + first-token latency, chars) |
| `latency_summary.md` | `models` | sync vs async vs streaming findings across providers |
| `review_analysis_<provider>.json` | `reviews` | structured analysis of all 10 reviews per provider |
| `review_provider_comparison.md` | `reviews` | schema validity, parse failures, label consistency, latency |

## Tests

The suite uses a **fake** chat model, so it runs offline with no API keys and
validates that the review pipeline returns output conforming to the
`ReviewAnalysis` Pydantic schema, and that parse failures are repaired by the
retry (`_fix_parse`) chain.

```bash
pytest
```

## Practical 1 - Prompt Templates

- Two reusable templates built with `ChatPromptTemplate.from_messages()`
  (system + human messages), including one with `{topic}` / `{tone}` input
  variables.
- `.format_messages()` is shown for both (works offline, no model needed).
- LCEL composition `prompt | model | StrOutputParser` is demonstrated when a
  provider is configured; otherwise the composed chain definition is printed.

## Practical 2 - Model Invocation Methods

Three providers (`ChatGroq`, `ChatMistralAI`, `ChatGoogleGenerativeAI`) are each
run through `invoke()`, `stream()` (tokens printed live), `ainvoke()` (asyncio)
and `astream()`. Total latency, first-token latency (streaming only) and output
length are captured into a comparison table and a markdown report.

### Findings (sync vs async vs streaming)

Interpret `outputs/latency_summary.md` once keys are configured. Typical
observations:

- **Streaming feels first**: `stream` / `astream` return their *first token*
  well before `invoke`/`ainvoke` finish the whole response, so interactive apps
  should stream for perceived latency.
- **Single-call async ≈ sync**: for one request, `ainvoke` latency is close to
  `invoke`; asyncio's real win is *concurrency* (many calls in parallel), not a
  single call. `astream` adds equally little overhead versus `stream`.
- **Providers differ in absolute speed**: Groq (GPU-inference) typically shows
  the lowest total latency, while provider identity affects both raw speed and
  first-token time. Because these are cloud APIs, absolute numbers vary with
  provider load and network, so relative comparisons matter more than any
  single sample.

## Practical 3 - Review Analysis Pipeline

`data/reviews.json` holds 10 realistic human-written reviews across products
and services with mixed sentiment. Each review is fed through a Runnable
pipeline `prompt | model | parser` where `parser` is a `PydanticOutputParser`
targeting the `ReviewAnalysis` Pydantic v2 schema:

```python
class ReviewAnalysis(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"]
    sentiment_score: float      # -1.0 .. +1.0
    key_issues: list[str]
    key_positives: list[str]
    summary: str
    recommended_action: str
```

Raw model text is fetched in one `.batch()` call (demonstrating LangChain
batching), then each output is parsed. On an `OutputParserException` the raw
output is **retried** by re-prompting the model with the schema instructions, the
invalid output and the parser error, then re-parsing (the same idea as the
removed `OutputFixingParser`, reimplemented as a small `prompt | model | parser`
chain in `_fix_parse`). This keeps the run from crashing on one bad output.
Results are saved per provider, and a comparison report covers schema validity,
parse failures, label consistency vs the star rating, and per-review latency.

### Findings

Once run, `outputs/review_provider_comparison.md` reports:

- **Schema validity / parse failures** — how reliably each provider emits
  schema-conforming JSON (lower is better).
- **Label consistency** — how often predicted emotion matches the human star
  rating (positive for 4-5 stars, negative for 1-2, neutral at 3).
- **Performance** — total and average-per-review batch latency per provider,
  which drives cost of processing large review sets.

`PydanticOutputParser` guarantees the *shape* of the output; quality differences
between providers show up as parse failures, label accuracy, and verbosity in
`raw_model_output` (kept in the output JSON for inspection).
